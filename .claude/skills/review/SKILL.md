# 리뷰 단계

## 목적
사용자가 작성된 코드를 완전히 이해하고 피드백을 줄 수 있도록 코드를 설명한다. 단순히 코드를 전달하는 게 아니라, 왜 이렇게 만들었는지 함께 공유하는 시간이다.

## 절차

### 1. 전체 흐름 설명
작성한 코드 전체가 어떤 목적을 위해 어떤 순서로 동작하는지 2~4문장으로 설명한다.
- 이 코드가 해결하는 문제
- 데이터나 흐름이 어떻게 이동하는지 (입력 → 처리 → 출력)
- 핵심 구조나 패턴

### 2. 줄 단위 설명
코드를 위에서 아래로 순서대로 훑으며 각 줄 또는 의미 있는 블록 단위로 설명한다.

좋은 설명의 기준:
- "변수를 선언합니다" ❌ → 코드를 한글로 번역하는 수준
- "let 대신 const를 쓴 이유는 이 값이 바뀌지 않기 때문입니다" ✅ → 선택의 이유

설계 단계에서 합의했던 내용과 다르게 구현된 부분이 있다면 그 이유도 설명한다.

### 3. 검증 체크포인트 — 1개씩 확인
설명이 끝나면 아래 항목을 **하나씩** 제시한다. 사용자가 각 항목을 확인하고 응답하면 다음 항목으로 넘어간다.

항목마다 아래 형식으로 제시한다:
```
(N/8) [항목 내용]
1. 확인 완료
2. 문제 있어 (어떤 문제인지 말해줘)
3. 해당 없음
```

**코드 확인 항목 (4개)**
1. 내가 설계한 대로 만들었는가?
2. 이해 안 되는 코드가 있는가?
3. 내가 요청하지 않은 것이 들어왔는가?
4. CLAUDE.md 금지 패턴이 포함됐는가? (any 타입, 외부 라이브러리 등)

**브라우저 확인 항목 (4개)**
5. 의도한 레이아웃으로 보이는가?
6. 로딩 상태가 노출되는가?
7. 에러 상태가 처리됐는가?
8. 개발 환경에서만 동작하는 코드가 없는가? (fetch('/src/data/...') 같은 패턴)

"문제 있어"를 선택하면 해당 문제를 즉시 처리한 뒤 다음 항목으로 넘어간다.

### 4. CLAUDE.md 금지 패턴 업데이트 검토
모든 체크포인트를 통과하면, 이번 구현에서 나온 패턴 중 **앞으로 모든 코드에 적용해야 할 규칙**이 있는지 능동적으로 검토한다.

추가할 만한 규칙이 있으면 제안하고 사용자 동의 시 CLAUDE.md의 `### 금지 패턴 (server)` 또는 해당 섹션에 추가한다.
추가할 내용이 없으면 이 단계를 건너뛴다.

### 5. 피드백 요청
CLAUDE.md 업데이트(또는 건너뜀) 후 아래 형식으로 피드백을 요청한다.

```
모든 항목 확인 완료. 추가로 수정하고 싶은 게 있나요?
1. 수정할 부분이 있어
2. 이해 안 되는 코드가 있어
3. 좋아, 커밋하러 가자
```

## 완료 조건
- "수정할 부분이 있어" 또는 "이해 안 되는 코드가 있어" → workflow가 `confirm` 스킬을 발동한다
- "좋아, 커밋하러 가자" 또는 동의 표현 → workflow가 `commit` 스킬을 발동한다
