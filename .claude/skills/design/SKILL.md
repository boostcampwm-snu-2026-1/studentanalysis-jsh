# 설계 단계

## 목적
구현에 들어가기 전에 무엇을 어떻게 만들지 사용자와 합의한다. 이 단계가 탄탄할수록 구현이 빠르고 수정이 줄어든다.

## checklist.md 구조 전제

checklist.md는 아래와 같이 큰 feature 항목 아래 하위 항목으로 구성된다:

```
- [ ] feature/1: 학생 관리
  - [ ] 학생 등록 API
  - [ ] 학생 목록 조회
  - [ ] 학생 상세 조회
- [ ] feature/2: AI 분석
  - [ ] ...
```

하나의 feature 브랜치 = 하나의 큰 feature 항목 (하위 항목 전체 포함)

## 절차

### 1. checklist.md 읽기
프로젝트 루트의 `checklist.md`를 읽고 `- [ ]`로 표시된 **최상위 feature 항목** 중 가장 위에 있는 것을 선택한다.

checklist.md가 없으면: "프로젝트 루트에 checklist.md가 없어요. 만들어서 작업할 항목을 추가해주세요." 라고 안내하고 종료한다.

미완료 항목이 없으면: "checklist.md의 모든 항목이 완료되었어요!" 라고 안내하고 종료한다.

### 2. 하위 항목 확인
선택한 feature의 하위 항목 목록을 사용자에게 보여준다.

하위 항목이 너무 크거나 모호하다면 더 작은 단위로 나눌 것을 제안한다. 사용자가 동의하면 checklist.md 수정을 부탁한 뒤 다시 시작한다.

### 3. 구현 방법 인터뷰
사용자가 생각하는 구현 방향을 먼저 들어본다. 한 번에 모두 묻지 말고 자연스럽게 대화하며 아래 내용을 파악한다.

- 어떤 파일을 수정/생성할 것인지
- 어떤 방식으로 구현할 것인지 (라이브러리, 패턴, 접근법 등)
- 이미 알고 있는 제약 조건이나 요구사항

### 4. 비판적 검토 및 개념 제시
사용자의 설계 방향을 파악했으면, 그 방식에서 발생할 수 있는 문제나 더 나은 방법을 능동적으로 찾아낸다.

단순히 문제를 지적하는 게 아니라, **관련 개념을 짧게 소개한 뒤 이 상황에서 어떻게 적용하면 좋을지 사용자가 스스로 생각해보게 질문**한다.

검토할 항목:
- **오류 가능성**: 예외나 버그가 발생할 수 있는 상황
- **비효율**: 더 간단하거나 성능이 좋은 방법이 있는 경우
- **누락된 케이스**: 사용자가 언급하지 않았지만 처리해야 할 상황

질문 형식:
```
[개념 이름]이라는 게 있는데, [한 줄 설명]이에요.
이 부분에서는 어떻게 적용하면 좋을 것 같아요?
```

문제가 없으면 질문 없이 넘어가도 된다.

### 5. 설계 요약 제시
인터뷰가 끝나면 합의된 내용을 아래 형식으로 요약해서 보여준다.

```
## 설계 요약
- feature: [feature 항목명]
- 하위 항목: [하위 항목 목록]
- 수정/생성할 파일: [파일 목록]
- 구현 방식: [합의된 접근법]
- 주의사항: [엣지 케이스, 제약 조건]
```

### 6. feature 브랜치 생성 안내
설계 요약이 확정되면 사용자에게 아래 명령어를 보여주고 직접 실행하도록 안내한다.

브랜치 이름은 GitHub Issue 번호와 기능명을 조합한다:
```
git checkout -b feature/[이슈번호]-[기능명] origin/dev
```

사용자가 브랜치 생성을 완료했다고 하면 다음 단계로 넘어간다.

### 7. 문서 반영
설계 과정에서 사용자가 수용한 개념이나 결정사항을 문서에 반영한다.

**반영 기준:**
- `CLAUDE.md`: 아키텍처 결정, 라이브러리 선택, 구현 방식 제약 등 프로젝트 전반에 영향을 주는 내용
- `checklist.md`: 해당 항목 옆에 결정된 기술/방식을 인라인 메모로 추가 (예: `(mongoose 사용)`)

반영할 내용이 없으면 이 단계를 건너뛴다.

## 완료 조건
브랜치 생성 확인 + 문서 반영(또는 건너뜀) 후 사용자가 진행에 동의했을 때 → workflow가 `implement` 스킬을 발동한다
